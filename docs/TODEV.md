## 开发清单

1. **OIDN 降噪可开关 + 随机噪点注入**
   - 将 OIDN（Open Image Denoise）设置为可手动开关的模式。
   - 关闭/调参后，让 RoboTwin 生成的测试与训练数据中产生随机、可能出现噪点的样本，用于测试方法（EMIX）在含噪输入下的有效性/鲁棒性。
   - **进展（2026-09-22，已提交）**：已实现 `ROBOTWIN_RT_DENOISER` 环境变量开关（`third_party/RoboTwin` `2de39e7`，默认 `oidn` 保持历史行为，`none`/`optix` 可选）。
   - **实测发现（重要）**：32spp 路径深度 8 下，svulkan2 RT 渲染在平坦区域完全收敛（禁用 OIDN 后平坦区 std=0.00，两次独立渲染逐像素一致），**关闭 OIDN 不会产生可见噪点**；且 JPEG(q95) 编码 + 84×84 降采样会进一步抹掉残余颗粒。另发现 emix-twin 环境的 OIDN 插件在本机 4070 上一直初始化失败（"OIDN Error: invalid handle/unsupported device type"），历史批次中经 4070 采集的任务实为无降噪渲染。若需要真实噪点，必须额外降低采样数（如 spp 8→2，属第二个变量，需用户确认）。
   - **修正（2026-09-29，用户人工目检确认）**：上述"无可见噪点"结论仅适用于 **40 系卡（4070）**——OIDN 初始化失败时 RT 直接收敛出干净图。OIDN 错误出现在 **50 系卡（5060）**上时，渲染图**确实有可见噪点**，其机理为**随机明暗偏移**（亮度级扰动），不损害对任务操作物体的辨识，影响不严重；与本轮实验注入的逐像素独立高斯噪声**机理不同**（后者叠加在像素值上，可能干扰物体辨识）。历史数据按采集卡不同可能带不同程度的原始 OIDN 噪声：40 系卡采集的任务图像干净，50 系卡采集的任务图像带轻度明暗偏移噪声。
   - **进展（2026-09-28）**：按当前要求新增显式高斯噪声增强，无需重新采集或依赖 OIDN 开关。训练时对解码、缩放为 `[0,1]` 的 RGB 图像逐像素、逐通道独立采样 `ε ~ N(0, variance)`，得到 `clip(x + ε, 0, 1)`；没有整图亮度缩放。噪声加在 EMIX 混合之后、策略标准化之前，覆盖 baseline、mixed 模式的两种 batch 和纯 EMIX 模式。评估默认原始图像，可独立开启同分布噪声；正式条件由 [docs/_exp.md](_exp.md) 固定。
   - `image_noise.enabled` 默认 `false`，`variance` 默认 `0.0025`（标准差 `0.05`，255 色域等效标准差 `12.75`）；`variance: 0` 精确关闭。方差描述截断前的分布，黑白边界附近截断后实测方差可能较小。随机数独立于模型/加载器的全局 RNG，由训练 seed 和绝对 step 决定；相同 seed、step、输入 batch 可复现，重新读取同一帧在不同 step 会得到新噪声。
   - 噪声参数保存在训练快照和 checkpoint 的 `train_config.json`，不进入策略配置。评估只由 `evaluation.image_noise` 显式开启，并写入 metrics。开发使用方式见 [SOP-03](sop/SOP-03-model-training.md#23-高斯噪声训练与可控评估)；固定任务、模型、噪声条件、运行顺序及状态统一以 [唯一实验协议 `_exp.md`](_exp.md) 为准，本清单不另维护实验参数。
   - 此增强用于可控的含噪训练实验，不声称在统计上严格复现关闭 OIDN 的路径追踪噪声。V0 四臂成功率已记录在 `_exp.md`。
   - **进展（2026-09-28）**：emix-noise 协议（EMIX 混合训练 + 同样的显式高斯噪声）配置与执行器支持已就绪（两份 `configs/scripts/run_emix_noise_tn_{ec,en}.yaml`、`scripts/run_noise_experiment.py --status-prefix emix-noise` 独立台账）。同日用户确认 var000625/0.0025 两档均足够；最终决定**本轮沿用已执行的 var0025**（emixDP 臂配置回切 0025 并规范命名为 `v0-singleTask-noiseVar0025Tr/TrEv-emixDP-s5-seed0`，待 defaultDP 臂完成、GPU 空闲后启动）；var000625 留待后续轮次。协议命名与状态以 [docs/_exp.md](_exp.md)（V0 / 实验 2）为准。
   - **收官（2026-09-29 用户决断）**：历史 EMIX 正提升（can_basket、dual_shoes）很可能源于 50 系卡 OIDN 错误的含噪数据（机理为小幅明暗偏移，与高斯噪声不同，无法复现）；**噪声方向不再投入实验和计算资源**（var000625 轮次与 clean 对照臂冻结），TrEv 收尾后仅出收官分析。详见 [_exp.md](_exp.md) §3.6。
   - **新决断（2026-10-01）**：V0 轮次仍按历史记录封存；V1 重新采集数据后，排在 `v1-collage` 五任务/十任务之后运行 `v1-noise` 五任务/十任务，先训练含噪评估 clean，再复用训练评估含噪。此项覆盖上一条对未来噪声实验的冻结，不改写 V0 历史。

2. **EMIX 线性叠加 → 图像拼贴（Collage）方案**
   - 将当前 EMIX 的线性叠加（alpha-blend）方式替换为图像拼贴方案。
   - 目的：避免线性叠加可能带来的重影、困惑（ghosting / ambiguity）等问题。
   - **设计（2026-09-28；2026-09-29 通用标注模块已实现，拼贴训练待接入）**：与条目 3 共用仿真实例像素、任务对象表和逐帧阶段标注，具体接入见 [共同基础设施设计](design/semantic_augmentation_foundation.md)。仿真直接输出实例掩码，无需外部分割模型；拼贴后的双分支损失固定为 `L_A + L_B`，不除以 2。

   - **通用模块进展（2026-09-29）**：已实现实例编号紧凑映射、HDF5 无损压缩和 RGB/归属图同步抽帧、裁剪、缩放、翻转；11 项 CPU 测试通过。只做基本字段校验，不增加哈希。尚未接入真实仿真采集与训练，缩小造成的边缘和小物体问题暂不修复。
   - **V1 接入（2026-10-01）**：RoboTwin 采集同帧输出 actor ID，写入压缩 HDF5，并保存每 episode 的 actor ID→任务对象名表；转换为 84×84 的紧凑归属图。`Emix-collage` 仅选择一个可见任务对象像素从第二图粘到第一图，损失严格 `loss1+loss2`；旧方法统一命名 `Emix-overlay`。配置和五/十任务执行顺序见 [_exp.md](_exp.md#4-v1-后续实施计划)。

3. **分阶段增强（Phase-aware Mixup）**
   - 通过夹爪开合信号将任务手动划分为 pick / place 阶段：按时序，pick 动作之前的所有帧记为 **topick** 阶段，place 动作之前的所有帧记为 **toplace** 阶段。
   - 阶段划分约束：一个阶段的划分不得逾越（越过）任何一个 pick 或 place 切换点，即阶段边界只能落在夹爪开合事件处。
   - 分阶段增强规则：只增强任务的目标物体。例如 `pick apple on plate` 任务中，pick 阶段仅叠加 apple，place 阶段仅叠加 plate。
   - **实施方式**：针对少数任务分别写固定阶段规则，依据专家操作顺序及指定夹爪开合事件生成逐帧标签；共用存储和读取接口，不开发通用阶段识别器。具体事件记录、帧对齐和目标选择见上述共同设计；本次不额外改变未来动作窗口。

## 优先级评估（先做哪个最合适）

| 优先级 | 条目 | 理由 |
|--------|------|------|
| P0 | 1. OIDN 开关 + 噪点注入 | **已收官（2026-09-29）**：训练侧显式高斯噪声已实现并完成 var0025 本轮实验；噪声方向不再投入资源。 |
| P0 | 5. 摆放随机化尺度扩大 | 用户指定的优先 TODO；任务空间尺度是历史增益不复现的重要候选解释，且是后续一切采集/训练批次的输入条件，应先于方法改动冻结数据分布。 |
| P1 | 2. 线性叠加 → 拼贴 | 直接针对当前方法的核心缺陷（重影/困惑）。对象级拼贴需要先接通仿真实例掩码与对象表，再修改 EMIX 图像合成及双分支求和。 |
| P2 | 3. 分阶段增强 | 语义上最有价值（按任务阶段叠加对应目标物体），但依赖夹爪开合信号的可靠提取与阶段切分逻辑，且最好建立在干净的混合方案（P1）之上，否则阶段正确性难以归因。 |
| P3 | 4. push/pull/open/close 任务扩展 | 工作量最大（新任务环境、数据采集、标注、训练与评估全链路），且 open/close 的阶段划分可直接复用 P2 的阶段切分框架，因此应在分阶段增强验证可行后再扩展任务面。 |

**建议执行顺序：5 → 2 → 3 → 4（条目 1 已收官）。**

- 1 和 2 相互独立，可并行；若算力/人力允许，P0、P1 同步启动。
- 3 依赖 2 的干净混合结果；4 依赖 3 的阶段划分框架复用，故排在最后。
- 风险点：若 P2 拼贴方案在视觉一致性上反而引入新的接缝/遮挡问题，需要回退评估是否保留线性叠加作为对照组。
